# 撤销保护 v1：结果与边界

这次优化的是撤销策略，没有微调权重。三类告警中证据不足的“误报”判断变为 **保留告警、人工复核**，不把保留状态说成模型确认真错。桌面展示新增对应状态，原模型 isValid、概率和解释保留用于追溯；其他规则不受此策略影响。iOS 测试版原本已将模型误报建议保留供人工复核，本次没有重编译或修改 iOS。

## 主要结果

对上一轮 CPU 实际推理的 v7 paired 288 条结果应用新策略：

| 指标 | 之前 | 之后（保留/撤销操作口径） |
|---|---:|---:|
| 真错误撤销 | 56/144（38.89%） | 4/144（2.78%） |
| 真错保护召回 | 61.11% | 97.22% |
| 误报撤销率 | 68.75%（99/144） | 44.44%（64/144） |
| 撤销精确率 | 63.87%（99/155） | 94.12%（64/68） |

storage 的 24 次、spelling 的 17 次、ratio 的 11 次真错误撤销均转人工复核；剩余 4 次属于 key_type，本次未扩大到该类。共 87 条转人工复核，其中 52 条真错、35 条误报，平均每条告警增加 0.302 次待复核。模型本身的准确率仍为 64.93%，不是 97.22%。

五组数据、18 份历史预测和 1 份上轮 CPU 预测均已重新通过生产策略计分，逐组前后比较见 [report.md](report.md)，完整分类指标和错误 ID 见 [scores.json](scores.json)。各组不合并为总分。模型未变化，因此复用固定预测以隔离策略效果，没有重复加载模型推理，也未新增设备性能结论。

## 实现

- storage / text_number / type_mismatch：现有请求未提供足够的原始单元格类型及转换证据，误报建议需要复核。
- ratio / 对应比例和百分比告警：缺少可机器核验的业务要求和单位定义，误报建议需要复核。
- spelling / function_spelling：调用名不在现有内置函数列表、无法提取或存在未闭合字符串时需要复核。列表不全的合法新函数、UDF、命名 LAMBDA 也会复核，不据此宣称它们是真错；已知函数名只允许沿用原模型对拼写告警的判断，不能证明整个公式业务正确。
- 保护在响应解析和合并入口都应用；模型不能通过输出 review 字段跳过本地策略。没有按测试分数调整阈值。

benchmark 的策略路由使用既有规则类别和公式，**不读取 label/is_error/oracle 作为策略输入**。旧集合无独立 formula 字段时，从原 state 提取函数调用；无法提取则保守复核。gold 仅供评分。不是通用公式解析器，不用于执行表达式。

```powershell
npm --prefix app run test:native

```

本轮依据已暴露的错误类别作出调整，属于诊断后回归，不能宣称独立泛化能力。新策略没有解决模型的 storage/ratio 理解能力，而是把风险交回用户。后续应补充结构化类型、单元格引用和明确业务要求，在单独开发集验证可核验的撤销条件；再用新模板、独立题组的冻结集评估能否减少这 35 条额外误报复核，同时维持真错保护。不要直接针对本次已看过的 288 条放宽策略。
