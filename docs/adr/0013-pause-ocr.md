# ADR-0013：先暂停照片和扫描件的文字识别

## 背景

[ADR-0003](0003-input-pdf-and-images-local-ocr.md) 定了第一版收 PDF（文字型和扫描型）和照片，扫描件和照片用 Apple Vision 在本机识别文字。第②步新脱敏流程按这个做完了：原生读取器先读 PDF 的文字层，读不到再用 Vision 的精确模式识别，中英文都开着；遇到表格漏列，会分块再读一遍补上。

2026-10-21 jojo 担心系统自带的识别质量太差，问要不要先缓一缓。当时手上的事实：

- 识别只在自己生成的合成图片上验证过：干净、字号正常，含旋转、横放、轻微倾斜。从没在真实的扫描件、手机照片、热敏纸打印单上量过。
- 在合成化验单上见过精确模式整列丢字，补救的分块重读同样只在合成图上验过。
- 对脱敏来说，认错字有两种后果，都不显眼：
  1. 分享出去的文字就是识别结果。`5.6` 认成 `5.8`，或者少了一列，AI 读到的就是错的数，用户从代号和排版上看不出来。
  2. 姓名或号码认错，规则就可能认不出来；残留检查也只能比对认对了的值，于是一个“几乎一样”的个人信息会被放出去。

文字型 PDF 和粘贴的文字没有这两个问题：分享出去的就是原文。

## 决定

这一版只收**文字型 PDF 和粘贴的文字**：

- 照片不读，读取页写明原因：需要识别文字，这一版先不支持。
- 扫描页不读，同样写明原因。一个扫描件有几十页时，合成一行“第 1–30 页”。
- 一页画了图片、而且文字层不到 200 个可用字（比如扫描件加了打印的页脚）：文字层照常读，同时提示这一页的图片部分没读。这一页不会自动进复核，要用户点“跳过出错的部分”。
- 没画图片的页照原样读，哪怕只有一行字（“报告医师：…”）或者是空白页，不报错。
- 文字层解不出来的页（字体没有字符映射，读出来是乱码）不读，同样写明原因。
- 选择文件的对话框只列 PDF。界面文案里不再提照片和识别。
- [ADR-0012](0012-redaction-flow-defaults.md) 第 1 条“新流程只收 PDF、照片和粘贴的文字”相应收窄：照片和扫描件按这条暂停。

识别的代码留着，没有删：

- 总开关是 `app/shared/redact/features.ts` 里的 `OCR_ENABLED`。
- 原生读取器加了 `--text-only` 模式，主进程按开关决定传不传。选项只认 `--` 之前的，主进程总是把文件路径放在 `--` 之后。
- 原生测试（`cd app && npm run test:docreader`）在合成图上跑完整的识别路径。它不在 CI 里，暂停期间没有自动守着；打开开关之前必须手动跑一遍。
- 文案用 i18next 的 context：现在的文案是默认键，识别打开时的文案在 `*_ocr` 键里，开关一改就跟着变。
- 端到端测试“文字型 PDF 加照片”按开关分两支：关着时断言照片被拒并写明原因，开着时断言照片读出来、和 PDF 用同一个代号。

ADR-0003 里不变的部分：识别回来时仍优先用本机的 Apple Vision（或另立 ADR 换本机模型）；粘贴文字仍是附带入口；这一版不输出打码后的图片或 PDF。

## 考虑过的方案

| 方案 | 结果 | 理由 |
|---|---|---|
| A. 照旧识别照片和扫描件 | 否决 | 覆盖面最大，但真实质量没量过；认错的字会无声地进到 AI 的输入里，也会让残留检查漏掉 |
| **B. 先暂停识别，只收文字型 PDF 和粘贴** | **采用** | 分享出去的就是原文；开关一改就能恢复，代码和测试都留着 |
| C. 保留识别，但加一步强制核对（原图和识别结果并排，用户确认才继续） | 否决 | 覆盖面保住了，但界面工作量大，用户也未必看得出数字认错 |

三行是 2026-10-21 问 jojo 时给的选项。推荐 B，jojo 选了 B。

## 接受的代价

- 手里只有纸质报告、照片或扫描件的用户，这一版用不了，只能自己把文字粘贴进来。
- 和定位有差距：[ADR-0002](0002-position-personal-medical-records.md) 写着“医疗档案很多是扫描件和照片”，jojo 在 [ADR-0003](0003-input-pdf-and-images-local-ocr.md) 里也说过“医疗档案一般都是 pdf 和图片”。
- 演示时不能再直接用手机拍的体检单。

## 后果

**好处**：

- 分享出去的文字和原文件逐字一致，医学数值不会因为识别出错而变。
- 残留检查比对的就是原文，不会因为认错而漏。
- 读取更快，不再耗 CPU 做识别。

**风险**：

- 扫描仪或手机 App 生成的“可搜索 PDF”自带一层识别出来的文字层，质量同样未知。文字层够长（200 字以上）的页会被当成文字型 PDF 读进来，不提示。
- 文字很多（200 字以上）的页里嵌着的扫描图片（贴进去的化验单截图、签名图）不读，也不提示：这部分内容会从分享文字里悄悄少掉。不提示是为了不让每页都有医院 logo 的文字型 PDF 页页报错。
- 用户可能把“不支持我的文件”理解成产品不能用，而不是“这一版先不做”。

## 重新评估的条件

- 在本机用不少于 50 页真实的扫描件和照片量过：医学数值和个人信息字段的逐字错误率都不高于 0.5%，并且没有整列丢失。样本用本机的真实病历（只在本机读取，不进仓库，读原件前要病历所有人确认）或 Black Sky 的数据集。达标就提议打开开关。
- 或者决定换一个本机中文识别模型（例如 PaddleOCR）：按 [ADR-0011](0011-on-device-inference-bottom-line.md) 另立 ADR，量过同样的线再打开。
- 或者 GitHub issue 和 jojo 收到的用户反馈里，累计 5 份以上说扫描件或照片读不了：提前讨论上面两条。
- 读取器这个原生小程序在签名、公证或 App Store 审核上走不通（从 ADR-0003 继承，文字型 PDF 也要靠它读）。

## 复盘（Q1–Q5）

### Q1. 上一版做对了什么（这次保留）

在本机识别、不联网；先读 PDF 文字层，读不到才识别；粘贴文字作为附带入口；不输出打码图片。读取器的结构和识别代码都留着，开关一改就能回来。

### Q2. 上一版做错了什么

ADR-0003 把识别放进第一版时没有定质量线，也没有安排在真实样本上量。它的“接受的代价”只写了“认错的字会变成漏报”，没想到另一半：认错的医学数值会原样交给 AI。

### Q3. 为什么这次不是同一个坑

这次恢复识别有一条可以量的线：真实样本不少于 50 页，医学数值和个人信息字段的逐字错误率不高于 0.5%，没有整列丢失。识别代码和它的原生测试都留着；打开前手动跑一遍原生测试，坏了就先修。

### Q4. 什么情况下回退

满足“重新评估的条件”里的前两条之一就提议回退：先手动跑 `npm run test:docreader`，再把 `OCR_ENABLED` 改成 `true`。文案、选择文件对话框、读取器和端到端测试会一起切回识别模式，然后跑一遍完整的端到端测试。

### Q5. 遵守了哪些教训

- 核心数据源出问题就停下报错，不输出缺地基的降级结果：识别结果是分享文字的唯一来源，质量没量过时宁可不读，也不把可能认错的内容交出去。
- [ADR-0003](0003-input-pdf-and-images-local-ocr.md) 自己的重新评估条件里写过“要讨论是否先收窄到文字型 PDF”，这次照做；只是触发点是没量过的风险，不是量出来的数据。
